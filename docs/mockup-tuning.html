Remuda — the tuning loop

Seven features that deepen the one thing Remuda already does that no other Ollama GUI does: edit → reload → retest. Mockups are built from the shipped design tokens, so what is drawn here is what the app can render.

The premise every screen below is checked against. Every competing Ollama GUI — Open WebUI, Msty, Enchanted, Chatbox, LM Studio — is a chat window, and competes on chat surface. Remuda does not win there. Remuda's user is the person tuning a model, and the loop they run is the product. Nothing here is a chat feature.

T1 · SMALL · BUILD FIRST

Modelfile history — the undo the loop never had

Remuda's pitch is that the edit→reload→retest loop is fast. A fast loop makes mistakes fast too, and the failure it creates is specific: "I had it behaving three saves ago and I can't get back."

Every Save already funnels through one path and rawText is already the declared source of truth (SPEC §6), so this is a store slice and a diff view. No new API calls.

Restore does not create. It loads the snapshot into the editor as an unsaved draft and switches to Raw. It does not run ollama create and does not reload the model — the user still hits Save, which goes through the normal confirm. A history feature that silently rebuilds a model on click is a trap, not a safety net.

Drift is surfaced, not resolved. The top entry appears only when the live file hashes to nothing in the ring — someone edited it outside Remuda. That is SPEC §12 question 4 observed rather than answered, and saying so is better than showing a stale snapshot as "current".

Sizing. Modelfiles run 1–2 KB, so a 40-deep ring per model is ~80 KB — an order of magnitude under the budget that forced image thumbs in SPEC §6.

T2 · MEDIUM · THE FLAGSHIP

A/B run — one prompt, two configs, both sets of numbers

The thing the audience already does, badly, in two terminal windows with a scrollback buffer between them. It is the actual question behind every Modelfile edit — is this better? — and today Remuda answers it the way ollama run does: by making the user remember what the last answer looked like.

No local Ollama GUI does side-by-side. It is the most visible differentiator on this list.

Message both lanes…

Seed is pinned for the pair, or the comparison is noise. When neither lane sets seed, Remuda pins one shared random seed and says so on the bar. Comparing two configs under two different seeds measures sampling noise and nothing else — shipping that quietly would be worse than shipping no comparison at all.

Sequential, deliberately. Lane A runs to completion, then B — so SPEC §8's one streamed generation at a time is preserved exactly. The reason is not convenience: two concurrent generations contend for the same VRAM, and the tok/s under each lane would be measuring the contention rather than the configuration. Lane B shows queued, then warming, then tokens.

The win markers are per-metric and there is no aggregate score. Remuda marks which lane was faster on each number and stops there. "Which is better" is a judgement the product should not pretend to make — that's what the human is for, and it's why Keep this side is a button rather than a computed recommendation.

Different models cost a swap, and the bar says so before the run — running two models back to back unloads one and loads the other. Same model, different parameters is the fast path and the common one.

T3 · MEDIUM

Tool-calling playground — is this model's function calling actually any good?

A question every developer evaluating a local model has, with no way to answer it in any GUI — you write a script. Remuda already parses the tools capability off /api/show and already gates UI on capabilities.

The differentiator is the validation verdict, not the rendering. A chat window that pretty-prints tool calls is a nicety. One that says unit: not in enum [celsius, fahrenheit] in red is a test harness — a different product.

The tally is the answer. 7 calls · 5 valid · 2 malformed is what turns a session into a finding you can act on — it's the difference between "the model called a tool" and "this model gets function calling wrong 30% of the time on my schema."

A plain reply to a tool-shaped prompt is a finding, not an error. A model that lists tools can still answer in prose. The transcript records it as such rather than swallowing it.

Wire detail that will bite. Ollama returns tool_calls[].function.arguments as an object, not a JSON string — unlike the OpenAI format it borrows from. The parser must not "helpfully" JSON.parse it. The validator is a hand-rolled subset — type, enum, required, properties — and deliberately not a dependency.

T4 · MEDIUM

Fit predictor — where does this model stop fitting?

Remuda already shows the amber spill chip after a model has spilled into system RAM, when the only remedy is to unload and try again. The useful moment is the one before, and the parameter the user would actually change is num_ctx — which is exactly the one that drives the KV cache.

It is an estimate and it says so, in the same line as the number. bytes_per_element assumes an f16 KV cache; a user running OLLAMA_KV_CACHE_TYPE=q8_0 halves it and no endpoint reports which is in force. So every figure is prefixed ≈ and the third line names its own provenance — estimated versus calibrated from your last load.

The estimate self-corrects. After a real load, /api/ps reports actual size_vram. Remuda stores actual / predicted per model and folds it into the next prediction — the second time you touch a model, the number is measured rather than modelled.

An architecture that doesn't report gets no guess (third pane). No fit track, no fabricated number, and a sentence saying what was missing. A wrong prediction here costs the user a five-minute load.

Green and amber are the same semantics as the top-bar spill chip, so the prediction and the readout read as one idea at two points in time.

T5 · LARGE · BUILD LAST

Bench — the regression test for a Modelfile

A saved set of prompts, replayed on one click, each answer diffed against the last run. It is T1 and T2 composed — snapshots to run against, a diffed comparison to render — which is exactly why it comes last. Built first, it would force bad versions of both.

Same/changed is a diff, not a verdict. Remuda does not score answers and does not call one better. An LLM judge would make this a different and much less trustworthy product — and it is the line that keeps this from becoming the eval harness SPEC §1 rules out.

The run strip ties the results to T1. against terse-v2 @ 14:22 names the Modelfile snapshot the run was made against, which is what makes the history and the results one artifact instead of two. Unchanged rows collapse — the changed ones are the whole point.

Capture is one icon on any user message in chat: add to bench. A bench that costs a form to populate does not get populated.

T7 · SMALL–MEDIUM

Runtime telemetry — what the machine is doing, not just what the model weighs

Host RAM used against total, the Ollama process's CPU load, GPU utilisation where it can be read honestly, and the share of the context window this chat has actually spent. T4 predicts fit before a load; this reports it during the run. Same idea, two points in time.

First, a naming collision to fix

The existing 100% GPU chip is a placement figure — size_vram / size, meaning all the weights sit on the GPU. It is not GPU utilisation. Adding a real utilisation percentage beside it puts two chips reading "GPU" and a number next to each other, meaning entirely different things, in the same 40 pixels.

Context used is the most valuable thing on this list and it is free. ctx 8,192 names the window; it never changes and so carries almost no information after the first read. What the user needs is how much has been spent — because the consequence of running out is silent eviction of the oldest turns, which is invisible and is the single most common cause of "why did it forget?". Both counts are already in every /api/chat response.

GPU utilisation is a spike, not a commitment. On Apple Silicon there is no supported API. powermetrics reports it and needs root — out of the question for a cask that doesn't even sign itself. The non-root paths (IOKit AGXAccelerator PerformanceStatistics, or the private IOReport framework that macmon uses) are undocumented and have moved between macOS releases. Time-box it before the UI promises anything; the popover is designed to render correctly without it.

Every unavailable figure is absent, never zero — a missing hw.memsize, a server that omits context_length, an Ollama process that can't be found. Same one-sided-gate rule as SPEC §8: the cost of a wrong number in a diagnostic panel is that the user debugs the wrong thing.

Polling stays on the existing 5s /api/ps tick, and host stats ride along. CPU and GPU poll only while the popover is open. A telemetry panel that polls faster than its data changes is a battery drain in a menu-bar app's clothing.

SCOPE

What this deliberately does not add

No RAG, no prompt library, no personas, no cloud sync, no LLM-as-judge scoring, no multi-user. Each is a chat-window feature, each competes directly with products that have years of head start, and each pulls Remuda off the one axis where it is currently alone.

Build order: T1, then T2. T1 de-risks the loop everything else runs inside, and T5 is T1 and T2 composed — building it before them would mean building both badly. T7's context meter is free and can ride along with anything. T7's GPU percentage is the only item here that needs a spike before it is promised.
