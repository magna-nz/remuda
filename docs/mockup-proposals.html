Remuda — features worth borrowing from Ollama

Remuda already covers list, run, show, create, pull and rm. What it doesn't yet surface is most of what Ollama reports back — where the model actually ran, what it can do, and what it was thinking — plus the one knob you reach for constantly while tinkering: per-request options. Five proposals, in the order I'd build them.

Against Ollama v0.32.15 · mock data taken from the models installed on this machine
01

Runtime readout — what ollama ps knows and Remuda throws away

Remuda calls /api/ps already, but reduces the whole response to one boolean: isLoaded. The response also carries size, size_vram, context_length and expires_at — the PROCESSOR, CONTEXT and UNTIL columns of ollama ps.

That answers the question a local-model user asks more than any other: did it fit on the GPU, or is it spilling to CPU? A 27B Q4 that lands 100 % in VRAM and the same model spilling 38 % to system RAM feel like different products, and today Remuda shows the same green dot for both. It also makes Eject legible — you can see the memory you're about to get back, and the countdown you'd otherwise be waiting out.

02

Capability chips on installed models — and honest gates

Remuda already renders capability chips (tools, thinking, vision, embedding) in the Pull pane — but those come from the scraped library catalog, so they exist for models you don't have and vanish for the ones you do. /api/show returns capabilities for every installed model; Remuda parses the response already and ignores that field.

Beyond the badge, capabilities are what makes the rest of this list honest: the thinking control (§3) and the image button (§4) should exist only where the model supports them, rather than failing at request time. And loading an embedding model into a chat surface should say so up front instead of returning an error on the first message.

Cost: near nothing — listGroups() already issues one /api/show per model and caches the result; this reads one more field off it.

03

Thinking — the reasoning stream, folded away

Both models installed on this machine report thinking. Ollama streams reasoning in its own field (message.thinking) and takes think: true or a level ("low" | "medium" | "high") per request — the API behind ollama run --think. Remuda reads only message.content, so today the reasoning is silently dropped.

For a UI whose whole purpose is testing whether a model is any good, the reasoning trace is the most diagnostic thing on screen — it's where you see the model misread the system prompt you just wrote. Collapsed by default so it never crowds the answer; live-streaming into Thinking… while it's generating, then collapsing to a one-line summary with the time spent.

APIPOST /api/chat { think: true | "low" | "medium" | "high" }message.thinking

Given 10M mostly-sorted integers, which sort should I reach for?
Qw

“Mostly sorted” is the load-bearing word here. Comparison sorts that assume randomness give up their advantage — I should be thinking about adaptivity, not just asymptotics.

Timsort is adaptive: it finds existing runs and merges them, so nearly-sorted input approaches O(n). Insertion sort is adaptive too but O(n·d) where d is the displacement — fine if the disorder is local, bad if a few elements moved far.

Radix sort ignores order entirely: always O(n·k). At 10M it's competitive on raw throughput but wins nothing from the existing order, and it costs memory.

So: recommend Timsort, name the condition under which radix would beat it.

Reach for Timsort — it's what sort() already gives you in Python, Java and Rust's sort_by. It detects the runs your data already has and merges them, so “mostly sorted” lands close to O(n) instead of O(n log n). Only reach for radix if the integers are bounded and the input's order is incidental rather than nearly-correct.

04

Run controls — try a parameter without re-creating the model

Today the only way to try temperature 0.9 in Remuda is: open the Modelfile editor, edit, Save as…, wait for ollama create, wait for the reload, then chat. That's the right ceremony for a change you want to keep, and far too much for the question “is this better at 0.9?”. Ollama takes an options object on every /api/chat call — the API behind /set parameter in ollama run.

So: a run-controls popover that overrides for this chat only, showing which values are inherited from the Modelfile and which you've overridden — and a Bake into Modelfile button that hands the winning values to the editor Remuda already has. That closes the tinkering loop the app is named for: try loosely, keep deliberately.

The rule that keeps it honest: overrides are per-session and never silently persist — the pill counts them, the note under each reply names them, and the Modelfile stays the source of truth until you press Bake, which opens the existing Save as… flow pre-filled. Bonus, nearly free: the stats strip. Ollama's final chunk already carries load_duration, prompt_eval_count/duration and eval_count/duration — Remuda uses two of the six for its tok/s figure. Prompt-eval rate is what you actually watch when you raise num_ctx.

05

Two small ones: images in, and quantise on fork

Vision. messages[].images takes base64 image data, and the model list already tells you which models accept it. A paperclip in the composer, shown only for vision-capable models, is a small amount of code for a whole class of model that is currently untestable in Remuda.

Quantise on create. ollama create -q q4_K_M quantises as it builds. Remuda's Save as… already calls /api/create — adding a quantisation picker turns “fork this Modelfile” into “fork this Modelfile and make it fit”, which is exactly the move someone makes right after seeing the amber spill warning in §1.

Shortlist, ranked by value ÷ effort

FeatureWhat it buysEffort
1 · Runtime readout Answers “GPU or CPU?”, makes Eject and keep_alive concrete. Fields already in a response Remuda parses and throws away. small
2 · Capability chips Installed models get the badges the Pull pane already shows for registry ones — and gate §3/§5 honestly. small
4b · Full timings Prompt-eval rate vs generation rate, load time, context used. Four more fields off the final chunk. small
5b · Quantise on Save as… One flag on a call Remuda already makes; the natural follow-up to a VRAM spill. small
3 · Thinking Reasoning models currently render half their output. Highest value per line of code on this list. medium
4a · Run controls Closes the tinkering loop: try a parameter in one click, promote it to the Modelfile when it wins. medium
5a · Vision Makes a whole model class testable. Needs file handling and image persistence in sessions. medium
— · Structured output format takes a JSON schema. “Does this model reliably emit my schema?” is a real test, but a narrower audience. medium
— · Tool-calling bench Both installed models report tools. Genuinely useful, but a whole surface — define tools, watch calls, feed results back. large

What I'd deliberately leave out

  • Push / publish (/api/push) — already deferred in SPEC §12.6, and rightly: it's the one action in Ollama's surface that sends your work off the machine. It sits badly beside “Remuda binds to nothing and phones nowhere.”
  • Cloud models (ollama signin, -cloud tags) — same reason, more so. Ollama runs them on someone else's GPU; the README's local-by-default promise is a positioning choice worth keeping intact.
  • Embeddings as a feature (/api/embed) — off-purpose for a chat-first UI. Worth exactly the one thing in §2: don't pretend an embedding model can chat.
  • GGUF import (/api/blobs) — already deferred in SPEC §12.5; genuinely useful, genuinely a separate project (chunked upload, digest handling, file picker).
  • ollama cp — the client has copy() wired up with no UI, and “duplicate before I tinker” is a real instinct. But Save as… already covers it for the case that matters, so a second forking verb would mostly add confusion.
