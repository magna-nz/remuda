Remuda — “+ New”: one button, two things to make

The rail's primary action currently says + New chat and is disabled whenever no model is resident — a dead control with a tooltip reading “Load a model first”. Benchmarks are made from a different affordance entirely: a small + in the BENCHMARKS header, also disabled for the same reason.

This replaces both entry points with one live button, + New, which opens a two-item menu. New chat is the only branch that ever asks about a model, and only when the answer isn't already obvious. New benchmark never asks: a lane is a model and a Modelfile, picked on the benchmark page, and the weights load when you press Run.

Interactive · click the window below · mock data from a 36 GB machine
01

The button, and the menu behind it

+ New is never disabled. That is the whole point: the old button's disabled state was the app refusing to help at the exact moment a new user most needs it. “Load a model first” tells you what is wrong and gives you nothing to click.

Chat sits above Benchmark because it is the overwhelmingly more common thing to make, and because the menu should read top-down as most-used first. Both rows carry a one-line description — nobody arrives at this app already knowing what a benchmark is.

03

When the question gets asked — and when it doesn't

The rule is one line: ask only when the answer is genuinely ambiguous. A sheet that opens to say “pick the only option” is a click charged for nothing.

“Exactly one” already has a name in the codebase: activeModel, derived in state.tsx as the current chat's model if it's resident, else the first resident one. The two-or-more branch preselects that same value, so Enter reproduces today's behaviour exactly — the sheet costs a keystroke, not a decision.

04

New benchmark — straight to the page, always. It never asks.

Benchmark takes you to the benchmark page and starts one, whether or not anything is in memory. No model question, ever. A lane is a configuration — a model and the Modelfile it runs under — and you pick it on the page, next to the other lanes you are comparing it against. That is the only place the choice makes sense, because the choice is relative.

Loading is Run's job, and it happens after the lanes are set. Asking at creation time would charge for a load before you have said what you are comparing — and then charge again at Run for every other lane anyway.

Where the load actually lands

Run all is the moment weights are needed, and it is the honest place to state the cost — by then the lane list says exactly how many models and which. Remuda loads them in lane order, one at a time, so a four-lane run against a 27B never asks the machine to hold all four at once.

05

Before Run — the one memory question worth asking

Lanes run one at a time: lane 1's model loads, answers every prompt, and is only then replaced by lane 2's. So two big lanes never have to coexist, and “A and B together won't fit” is not a state this feature can reach.

What can collide is the model you were already chatting to. If Y is resident and a lane's model isn't Y, both are in memory at that moment — Y still held, the lane's weights loading beside it. That pair is the check, and it is a pairwise one, taken lane by lane.

for each lane L, at the moment L loads:
  L.model === Y.tag  →  reuse — already resident, nothing loads
  otherwise  →  Y.measured + L.predicted > usable  ?  collision

never   A.predicted + B.predicted  — lanes are sequential (run.ts rule 2)

Note the asymmetry: Y is measured, not predicted. It is resident, so /api/ps reports its real size and size_vram — a fact, not an estimate. Only the lane about to load needs predictFit. That makes half of every comparison exact.

The same check, as a lane-row hint

Because the architecture fields come back on a request Remuda already makes, the warning can sit on the lane the moment you pick the model — before Run, before the dialog. The dialog then stops being a surprise and becomes a confirmation of something already on screen.

while editing zero extra requests
1 qwen2.5:7b · Original in memory
2 gemma3:27b-q4_K_M · Original needs qwen2.5:7b unloaded
Run all still asks. The hint can be scrolled past; a wasted five-minute load cannot.

This costs one field on Model. listGroups is already calling /api/show per model and parsing the response — it keeps capabilities and contextLength from it and drops archParams, which is the one thing predictFit needs.

When the check can't be made

predictFit refuses to invent numbers, and it refuses in three real situations: no host-memory reading (no Tauri bridge), a discrete GPU (where system RAM says nothing about VRAM, so usableVramFromHostMemory returns null), or a server whose model_info omits the architecture fields. All three are ordinary, not edge cases.

unpredictable say so, don't block
Memory check skipped This machine has a discrete GPU, so Remuda can't tell how much VRAM is free. The run will load each lane and report whatever the server says.
Run all is not disabled by an unknown. An absent prediction is not a failed one.

This follows the rule the fit predictor already sets for itself: no prediction is a first-class result, never a fabricated number. Blocking Run on a figure Remuda couldn't compute would make the feature worse than not having it.

Decided

Both calls settled, and the second one changed on the evidence.

decided “Unload and run” does not reload Y afterwards
It matches Eject, which Remuda already ships: unloading hands the memory back, and the next message warms it again. A surprise 5.1 GB load landing after a multi-minute run — while you are reading the results — is an action nobody asked for. One addition: when Y is pinned (keep_alive: -1), unloading clears the pin, and the dialog says so in those words. The pin was deliberate, so removing it has to be an informed choice rather than a side effect.
decided Both — Run is the gate, the lane row is a free hint
I said this “wants a cache before it wants a UI”. It turns out the cache is already paid for: listGroups calls /api/show for every installed model on every refresh, and throws model_info's architecture fields away — Model keeps capabilities and contextLength but not archParams. Retain that one field and the lane-row check costs zero extra requests. So: a passive warning sits on the lane as you edit it, and Run all keeps the blocking dialog — because the lane hint can be scrolled past and a five-minute wasted load cannot.

Behaviour worth pinning down before anyone builds it

ThingBehaviour
DismissEsc closes the menu and returns focus to + New. Click-outside closes it. The sheet's Esc cancels the whole action — it does not step back to the menu.
KeyboardMenu opens on Enter/Space/↓ with the first item focused; ↑↓ move, Enter picks. In the sheet, ↑↓ move the selection and Enter is the primary button — so “+ New, Enter, Enter” is the fast path with several models loaded.

Loading is still explicitSPEC §5.1's rule holds — nothing loads until a button is pressed. For chat that press is the sheet's primary button; for a benchmark it is Run all — and §05's memory check runs before any of it. Opening the sheet loads nothing, and neither does creating a benchmark.

A benchmark still opens, but with no lane choices the editor is disabled and points at the same place. This is the one case where installed, not resident, is the real blocker.

Decided

The three calls, made. Each one is reversible if it reads wrong in the hand.

decided Chat first
Frequency wins. The discoverability problem is solved by the menu existing — today the word “benchmark” appears only in a rail header and a disabled +. Second of two, with a description and a ⌘B beside it, is not hidden. Making the common action the second item taxes every chat forever to fix a first-run problem.
decided Keep the one-resident shortcut
It reproduces today's newChat exactly, so it is not a regression, and with one model resident there is precisely one answer — a sheet would be asking a question with no second option. The predictability worry is real but already answered elsewhere: the bound model is spelled out in the rail row and the top chip, and the new chat's first screen names it (“Chatting with qwen2.5:7b”). It is never a secret, just never a question.
decided Keep “Load a different model…”, and state the eviction plainly
Removing it puts “I want a chat with a model that isn't loaded” back at a dead end one level down — the exact thing this redesign exists to remove. So it stays. But Remuda cannot predict which model gets evicted: no endpoint reports OLLAMA_MAX_LOADED_MODELS, and the constant appears in this codebase only in comments. So the sheet states the general fact and claims no number — the same rule predictFit holds itself to.
