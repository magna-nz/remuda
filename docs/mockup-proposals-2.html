Remuda — round two, from Ollama's unused surface

The first round took what Ollama reports back. This one takes the parameters Remuda still never sends — format, raw, num_gpu — plus the one feature already specced and never built. Nothing here needs an account, an API key, or a network call off 127.0.0.1.

Sections 05 and 06 are the other half of shipping any of it: Remuda now does enough that a word like bench or compare means nothing on sight. Three layers of always-there help, and a five-step tour that survives Ollama not being installed.

01

Bench — the regression test for a Modelfile

The problem it solves. You tighten the system prompt so the model stops rambling. It stops rambling. Three chats later you notice it also stopped using the code fences you'd taught it two saves ago — and you have no idea which save did that, because the only evidence was a conversation you closed. Every edit to a Modelfile is a change to all behaviour, and right now Remuda lets you observe exactly one prompt's worth of it at a time.

What a bench is. A named set of prompts you've saved — the handful you always re-test after a change — replayed against the current model on one click, each answer diffed against what the same prompt returned last run. Not a score. Not a grade. A diff: this answer changed, that one didn't. You read the changed ones and decide.

It is T1 + T2 composed and almost no new machinery: T1 already snapshots every Modelfile save, T2 already runs a pinned seed and renders two answers side by side, and the diff renderer already exists in editor/diff.ts. A bench run is those three pointed at a list instead of a pair.

A bench that costs a form to populate does not get populated. So capture is a single item on the hover menu any user message already has — the same menu that holds Re-roll and Promote to SYSTEM. You are always in a chat when you discover a prompt worth keeping.

The rules that keep it a tool and not a scoreboard. Same/changed is a diff, not a verdict — Remuda never says one answer is better, because an LLM judge would make this a different and much less trustworthy product. One seed is pinned across every prompt in a run, for the same reason A/B pins one. Runs are sequential and cancellable; a cancelled run keeps its finished rows and is marked partial rather than thrown away. An errored row is a real result and stays visible — row 05 above is telling you your num_ctx is too small, which is exactly the kind of thing a bench is for. And the header names the T1 snapshot each run ran against, which is what makes the Modelfile history and the results one artifact instead of two.

02

Constrained output — format, the parameter Remuda never sends

What Ollama does. /api/chat and /api/generate both take a format field. Give it a JSON Schema and Ollama constrains decoding to it — the sampler is only ever allowed to pick tokens that keep the output valid against your schema. It is not prompt-engineering and it is not a retry loop; malformed JSON is unreachable by construction. Remuda passes format on exactly zero of its requests.

Why it belongs here specifically. Half of Modelfile tuning is trying to make a model emit a shape — “answer with JSON like this”, wedged into SYSTEM, then a week of whack-a-mole as it drifts. format deletes that entire class of system prompt. The tuning question changes from “did it produce valid JSON” to the one that actually matters: given the shape is guaranteed, are the values any good?

And it is mostly already built. tools/validate.ts is a JSON-Schema validator with per-field verdicts, and the tool-call card in tools/ToolsView.tsx is its display. This is that same pair, pointed at the reply instead of the tool call.

The honest failure is the interesting one. Under format the model cannot emit invalid JSON — but it can be cut off mid-object when num_predict runs out, and then you get a broken string and no explanation. The second card names that directly instead of showing a red parse error. It is the single most common way constrained output goes wrong, and no GUI I've seen tells you which of the two it was.

Three states, not two — Schema, plain json mode (Ollama's older format:"json", valid JSON with no shape), and off. It is per-chat and never persists, exactly like Run controls, because format is a request parameter — there is no PARAMETER format, so there is nothing to bake and the pane shouldn't pretend otherwise. Copy as curl picks up the format body for free.

03

The rendered prompt — the string the model actually receives

The blind spot. Remuda is a Modelfile tuning tool that will not show you what it sends. You write SYSTEM, Ollama pastes it into the model's TEMPLATE, wraps it in whatever control tokens that family uses, and hands the result to the runner. Remuda shows you the input and the output and nothing in between — so when a system prompt has no effect, there is no way to tell “the model ignored it” from “it never got there”.

Both of those happen, and they need opposite fixes. A hand-written or inherited TEMPLATE that never references .System silently drops your system prompt entirely; so does a MESSAGE-heavy file that pushes it out of the branch the template took. You cannot debug that from the chat window. You can read it in one glance here.

Where it goes. A fourth segment in the Modelfile editor, beside the three that exist — Form · Raw · Prompt · History. The template comes from /api/show, which Remuda already calls and already stores in ModelDetail.template; today nothing renders it.

The check in the left footer is the feature. “references .System” goes red the moment you are editing a Modelfile whose template cannot see your system prompt — which is the bug this pane exists to catch, and the one that costs people an afternoon.

Scope note, and it matters. Ollama has no “render this template” endpoint, so the right pane is Remuda executing a Go text/template subset in TypeScript. That is real work and it can drift from the server's own renderer. Two ways to stay honest: keep the substitution to the handful of actions real Modelfiles use (if, range, .System, .Messages, .Prompt, .Tools) and say “unsupported template action — showing the raw template” rather than guessing; and give the rendered pane a Send as raw… button that posts it back through /api/generate with raw: true, which bypasses templating entirely. If the raw send and the normal send produce the same answer, the render was right. That button is the pane's own test.

04

Embeddings — what they are, and the one version worth building

Plainly: what an embedding model is. You give it text, it returns a list of numbers — a few hundred to a couple of thousand of them. Text that means similar things comes back as similar numbers. That is the entire product. It does not chat, it has no system prompt, it has no TEMPLATE, and there are no sampling parameters worth touching. You cannot tune one, because there is nothing on it to tune.

So the honest answer to “should Remuda add embeddings” is: not as a feature of its own. An embed pane — paste text, look at 768 numbers — flatters nobody and teaches nothing. It is the kind of thing that gets built because the endpoint exists.

A correction to what I told you last time. I said Remuda lets you pull an embedding model and then silently does nothing useful with it. That was wrong — ChatView.tsx:129 already has an EmbeddingGate that names the model, says it has no completion capability, and explains why there's no composer. That hole was closed in round one. Nothing to fix.

The one version that earns its place — and it is blocked on Bench

Bench's changed/same is a string diff. That's the right default and it has one real weakness: reword a sentence without changing its meaning and the row goes amber, so a run where nothing meaningful moved still hands you six rows to read. An embedding of both answers gives you the distance between them as a number.

Crucially this is still a measurement, not a judgement — cosine distance says how far the answer moved, never whether it got better. It stays on the right side of the no-LLM-judge line the tuning spec draws.

run 7 · against terse-v2 @ 14:22 · seed 40412 2 changed3 same
Changed Rewrite this loop to bail early, and explain why in one line. 0.96
Changed Give me three names for a function that drains a queue. 0.41
Same Explain a mutex to someone who writes only Python. 1.00

Row 1 reworded and meant the same thing — 0.96, skim it. Row 2 came back with genuinely different names — 0.41, read it properly. That column is the difference between a bench you run and a bench you stop running.

the cost, stated up front

It needs a second model resident — an embedding model is 50–700 MB and has to be loaded alongside the one under test. Remuda's load pane, fit predictor and runtime telemetry are all written around one active model; that assumption would have to go, and the fit predictor would need to account for a passenger. That is the real price, and it is not small.

My recommendation: don't decide this now. Build Bench with the string diff, run it for a fortnight, and see whether the reword noise actually bothers you. If it does, this column is a well-scoped follow-up with an obvious payoff. If it doesn't, you've saved yourself the two-resident-models refactor. Either way there is nothing to build here today.

05

Help that is always there — three layers, none of them modal

Remuda now has a chat, a Modelfile editor with three sub-views, an A/B compare, a tool playground, a fit predictor, a runtime readout — and this round adds three more surfaces. A word like bench means nothing until someone tells you, and a tooltip you have to hover to discover is not telling anyone anything. So: three layers, each doing a different job, and a tour is not one of them — a tour you watched last Tuesday cannot answer a question you have today.

Layer 1 — the empty state, where “what is a bench?” gets answered

The best help costs nothing to find because you cannot avoid it. Every feature's first screen is empty by definition, and an empty screen that explains itself is worth more than any tooltip. Nobody reaches a bench without passing through this.

A bench is a set of prompts you re-run after a change

Every edit to a Modelfile changes all of a model's behaviour, not just the part you were working on. A bench replays your saved prompts against the new version and shows you which answers moved — so you notice the thing you weren't looking at.

Layer 2 — “About this pane”, one ? per surface

A ? in every pane header, toggling an explainer inline — it pushes the pane down rather than floating over it, so it can't cover the thing it's describing and it can't be dismissed by a stray click. Same three beats every time: what it is, why you'd use it, how. Open/closed is remembered per pane, so an experienced user closes each one once and never sees it again.

A saved set of prompts, replayed against the current model on one click, each answer diffed against what it returned last run. It is how you catch the behaviour you broke while fixing the behaviour you meant to.

Layer 3 — a glossary for the machine words

The identity of the app is human words in Inter and machine words in Plex Mono (SPEC §4). That split is already doing the work — so make every machine word a definition. Dotted underline, and the definition opens on hover, on focus, and on click, so it isn't hover-only for keyboard users. One shared glossary, one component, every surface.

Context length — num_ctx num_ctx

How much text the model can hold at once, counted in tokens — the conversation so far plus the reply it's about to write. Raising it uses more memory, and Ollama has to reload the model to change it.

A token is roughly ¾ of a word.

  · estimated fit uses the KV cache size · forked variants can be quantised on save

Cheap to build and it compounds. One <Term> component plus a flat glossary file. Every term you define is defined everywhere it appears — the load pane, the editor form, the run controls, the fit predictor — because they all render the same component.

06

The guided tour — offered on first run, re-runnable from Settings

The three layers above answer “what is this thing in front of me?”. They don't answer the question a brand-new user actually has, which is “what is this app for, and in what order do I do things?” That's a tour's job, and it's the only job it's good at — so it should be short, skippable, and never the only place a fact lives.

Four rules it has to obey. It is offered, never forced — a dismissible card, not a modal you have to escape before you can use the app you just installed. It runs on the real UI with real panes lighting up, not a slideshow of pictures. It must survive Ollama not being installed, which on a first launch is the likeliest state of the world, so no step may depend on a loaded model. And it is five steps, because nobody finishes fifteen.

The offer, first launch

First time here? Remuda in five steps.

About two minutes. You can stop anywhere, and re-run it later from Settings.

Ollama isn't running.

The tour still works — it explains what each part of Remuda is for. You'll need Ollama started before you can load a model and chat.

This pairing is the whole point. A first launch with no Ollama is the most likely first launch there is, and it's exactly when a tour that demands a loaded model falls over. This one doesn't, and it says so.
