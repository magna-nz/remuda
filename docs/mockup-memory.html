Where the runtime readout should live

Ollama holds more than one model in memory at a time. Remuda's UI was built as if it holds exactly one — the readout nested inside a single model's detail panel, and everything downstream inheriting that assumption. This was the proposal for pulling it out; it is now what the app does, with the two deviations noted in §02 and §04.

01

The assumption, and where it is written down

GET /api/ps returns a list, and parseRunning in api/client.ts already keeps every entry. The collapse happens one layer up, in ui/state.tsx:

// ui/state.tsx — deriveLoaded()
const loadedModel = models.find((m) => m.isLoaded);  ← the first one wins
if (!loadedModel) return null;

From there, loaded is a single object or null, and four surfaces read it as gospel: the top-nav model control names one model, Eject frees one model, New chat binds to one model, and the pane's In memory now block describes one model. Load a second and the app quietly stops describing reality — the weights are resident and answering, but nothing on screen says so.

02

Proposed: memory is the pane's front page

The load pane opens on a list of models you could load. Put what is already loaded above it, as its own section — one row per resident model, each with its own eject. The detail panel stays about the model you clicked; memory stays about the machine.

A totals line earns its place at this level, because the number that actually matters when you load a third model is the sum, not any single row.

Not built: the capacity meter sketched below as 2 of 3 slots. Ollama's ceiling is OLLAMA_MAX_LOADED_MODELS in the server's environment, and no endpoint reports it — the server may not even be on this machine. Rather than print a ceiling Remuda would be guessing at, the tray counts what it can actually see. The shipped footer reads 2 models in memory beside Eject all.

03

What the model detail panel keeps

Almost nothing. The detail panel is about a model on disk — its quants, its Modelfiles, and the one button that loads it. Its only remaining claim on runtime is whether this model happens to be resident, which is one line, not a card. Everything else moved up.

04

The part that isn't cosmetic

Moving the readout is a UI change. Supporting two is a state change, and it lands on one line:

// ui/state.tsx
- loaded: LoadedSelection | null
+ loaded: LoadedSelection[]        // [] when nothing is resident

Every consumer of the singular then has to answer a question it currently gets to dodge — which model. And for most of them the honest answer is already sitting on the session:

My read

Yes — move it, and yes, someone can load several. Ollama already does, /api/ps already reports it, and Remuda already parses the full list; the singular is imposed at exactly one line in deriveLoaded. That makes the readout's current home the symptom rather than the disease.

Built, in one pass rather than two. The split into "relocate first, then generalise" turned out not to be worth the seam: the tray is only interesting once it can hold more than one row, and the state change is a single field. loaded is now LoadedSelection[], joined by a new activeModel — the resident model an app-wide action gets when the user hasn't named one, which prefers the model the open chat already talks to and otherwise falls back to the first resident one. New chat, the Modelfile tab and the pencil in the nav all read activeModel; the tray, the nav chip and the unloaded banner read the whole list.

Two things landed differently from this sketch. The capacity meter is gone, for the reason given in §02. And the sidebar and chat banner needed less work than the table above first suggested — they were already asking about the session's own model rather than the global one.
